# DeepSeek-V4-Flash RL smoke on AWS GB300

Date: 2026-08-09

## Result

Both precision arms completed two GRPO rollout/training steps on 32 GB300 GPUs and exited successfully:

- BF16 training + FP8 rollout: Slurm `2934638`, W&B [`e1s53krn`](https://wandb.ai/megatron-core-moe-dev/miles-run_deepseek_v4/runs/e1s53krn)
- FP8 training + FP8 rollout: Slurm `2935340`, W&B [`cumrxk9s`](https://wandb.ai/megatron-core-moe-dev/miles-run_deepseek_v4/runs/cumrxk9s)

FP8 training did not accelerate this recipe. On the warm step, FP8 `compute_log_prob` was 44.2% slower and FP8 actor training was 45.8% slower. Reported total step time was 44.9% longer.

The train/rollout mismatch was also larger with FP8 training. Diagnostic KL was 42–44% higher and mean absolute log-probability difference was 21–22% higher across both steps. This is a consistent smoke-test signal, not an AIME accuracy result.

## Configuration

| Item | Value |
|---|---|
| Model | DeepSeek-V4-Flash-FP8 |
| Hardware | 8 nodes × 4 GB300 GPUs, one NVL72 segment |
| Training data | `zhuzilin/dapo-math-17k` |
| Algorithm | GRPO with math reward (`--rm-type math`) and rollout routing replay (R3) |
| Rollout batch | 32 prompts × 8 samples = 256 responses |
| Response limit | 4096 tokens |
| Trainer parallelism | TP2, PP8, CP2, EP4, expert TP1, sequence parallel, DP1 |
| Rollout parallelism | 8 SGLang engines, each TP4, DP1, EP4 |
| Placement | Colocated trainer and rollout |
| BF16 arm | BF16 Transformer Engine training; FP8 checkpoint rollout; FP8 KV cache |
| FP8 arm | Transformer Engine E4M3 blockwise FP8 training; FP8 checkpoint rollout; FP8 KV cache |

The Miles configuration selected `--fp8-recipe blockwise`, not its explicit
`--fp8-recipe mxfp8` path. Transformer Engine may implement block scaling on
Blackwell with MXFP8-compatible power-of-two scales; this report names the
recipe by the user-visible Miles/Megatron setting.

## Warm-step performance

| Metric | BF16 train + FP8 rollout | FP8 train + FP8 rollout | FP8 change |
|---|---:|---:|---:|
| Rollout time | 71.48 s | 73.20 s | +2.4% |
| Rollout throughput | 338.02 token/GPU/s | 326.02 token/GPU/s | -3.6% |
| `compute_log_prob` | 76.22 s | 109.93 s | +44.2% |
| Actor train | 100.45 s | 146.43 s | +45.8% |
| Actor train throughput | 8059.86 token/s | 5464.26 token/s | -32.2% |
| Reported step time | 334.70 s | 485.03 s | +44.9% |
| Sleep + weight update + wake | 69.31 s | 124.38 s | +79.5% |

Both arms use the same FP8 SGLang rollout path. Their rollout times are close; changing trainer precision is not expected to accelerate rollout.

The FP8 arm uses node-local NVMe for trainer sleep because the post-optimizer CPU backup does not fit beside colocated SGLang. The post-step backup occupied 273–528 GB per node depending on the PP stage. Disk sleep took 25.8–49.3 seconds across ranks and avoided the host OOM seen with CPU backup. These transition costs are separate from the FP8 training kernel times above.

AIME-2024 is present in the recipe, but evaluation was disabled for this two-step smoke. The runs therefore establish functional and numerical status, not downstream accuracy. A longer paired run with periodic AIME evaluation is required for an accuracy decision.

## Changes required by project

### Miles

The working path requires Miles changes:

- `miles/backends/megatron_utils/update_weight/hf_weight_iterator_direct.py` and `miles/utils/types.py`: carry the source expert's EP-local rank and translate it to the correct global root for each EP broadcast group. The previous root selection could give different roots to members of one group and hang weight sync.
- `miles/backends/megatron_utils/update_weight/update_weight_from_tensor.py`: rendezvous between weight buckets; the direct iterator also synchronizes CUDA work between PP, EP, and TP collective phases.
- `miles/backends/megatron_utils/rematerialize_utils.py`: retain backups for frozen parameters absent from Megatron DDP buffers. This is used by the BF16 CPU-offload arm.
- `train.py`: skip the final trainer offload and actor-to-rollout update when no later rollout or evaluation will consume the weights. This removes an unnecessary end-of-run OOM point.
- `miles/ray/train_actor.py`, both trainer group implementations, and `miles/ray/rollout/rollout_manager.py`: explicitly finish distributed tracking before Ray teardown so the last trainer and rollout rows reach W&B.
- `miles/utils/http_utils.py` and `miles/utils/arguments.py`: apply a finite rollout HTTP timeout so an incomplete response body can be retried.
- `scripts/run_deepseek_v4.py`: forward the deterministic NCCL environment used by the 32-rank weight update.

Miles already provides disk-backed trainer offload. No new offload implementation was needed; the FP8 run used `--offload-train-target disk` with `/raid/scratch` and disabled parameter rematerialization, as required by the existing validation.

### SGLang

No SGLang code change was required for functionality. The FP8 checkpoint, FP8 KV cache, TP4/EP4 engines, online weight updates, and two rollouts all worked.

SGLang reported that tuned GB300 FP8 W8A8 MoE configurations were missing for some shapes. Adding or autotuning those configurations is a rollout performance task; it is not required for correctness.

### Megatron-LM / Transformer Engine

No Megatron-LM or Transformer Engine code change was required. The existing distributed optimizer and Transformer Engine E4M3 blockwise recipe completed both FP8 optimizer steps.
